## 1. 起源与已否证的路径

初始问题：security-evaluation 的 code scan 能否调用 expert-review 技能。

结论（定论，有代码证据）：不能直接调用。code scan 是单文件、截断输入、无工具的单次调用，与 expert-review 存在五条硬不兼容：无跨文件与命令取证、严格 JSON schema 与 Markdown 报告形态冲突、severity 与 P0/P1/P2 两套严重度体系、服务侧写库并关闭历史 finding 与只读评审语义相反、缓存身份只含 content/prompt 哈希而评审需要 branch/HEAD 锚点。

可复用的是**方法条款**，不是技能本体。

## 2. 概念基线

三处容易混淆的归属：

| 层 | 内容 | 技能在这一层吗 |
|---|---|---|
| 权重层 | 预训练、RLHF、工具使用训练、长上下文训练 | 否 |
| 模型 API 层 | system prompt、tools schema、JSON mode、prompt caching | 部分，技能最终变成这里的输入 |
| harness 层 | 循环、上下文装配、技能加载、工具执行、权限、沙箱、观测、重试 | **是，技能是这一层的内容资产** |

技能不是 harness，而是**被 harness 执行的声明式配置 + 内容资产**。同一份技能在不同宿主效果不同，因为宿主提供的执行语义不同——可移植的是内容，不是效果。

效果分三层：

1. 语境注入：不提升能力上限，只消除"本可以做好但不知道"的失败。
2. 方法/程序：实质提升可达上限，但机制是"把单次采样换成有结构的尝试与核验"，不是模型变强。
3. 脚本/工具：已跨入 harness 领地，需要 shell、沙箱、权限模型。

术语歧义：harness 还有 eval harness（评测工装）的含义。技能属于 agent harness，不属于 eval harness；但断言技能有效必须依赖 eval harness。

## 3. 范围裁定

需求不是"设计一套 harness"——那会把循环、工具、权限、沙箱全部拉进来。需求是给 harness 补一个缺失的子系统。

| harness 部件 | 本需求 | 说明 |
|---|---|---|
| 上下文与技能装配 | 核心 | 任务类 + 技能集 → 确定性 prompt 产物 |
| 输出契约校验 | 需要 | 技能声明 schema，结果按契约验 |
| 调用身份与记账 | 需要 | 组合哈希进缓存键与结果，保证可复现、可归因 |
| 评测工装 | 需要 | 消融与回归；否则"更好"不可证 |
| 通用 agent 循环 | 不做 | 评估类调用是单次或固定阶段 |
| 工具与权限门控 | 不做 | 技能无副作用；副作用属于工具层 |

需求重述：为每一次 LLM 调用提供**可声明、可版本化、可校验、可度量、可复现**的方法装配能力，机制与业务无关。

命名建议：叫 **LLM 调用装配层**（skill composition layer），不叫 harness。叫 harness，后续工具、权限、循环的问题都会被提给这一层。

## 4. 架构提案（建议，未采纳）

四段链路：

| 段 | 职责 | 关键约束 |
|---|---|---|
| 资产 | 技能单元 | 不可变、内容寻址（id + version + contentHash）；文件形态；frontmatter 声明适用条件、层级、优先级、冲突关系、输出契约、token 预算 |
| 编译器 | 解析 → 链接 → 预算 → 发射 | 不调用模型；同输入产生字节相同产物；层序为基础 → 通用方法 → 任务方法 → 实例规则 → 运行级覆盖 |
| 执行器 | 调用模型、按契约校验、驱动程序型阶段 | 模型只做内容决策，控制流由框架固定 |
| 记账 | 组合清单 | 组合哈希、各技能贡献字节数、被裁掉项、阶段轨迹，进入结果与缓存键 |

调用方只声明任务类，可附加显式运行级覆盖，不自己拼 prompt。

缓存身份 = 模型 + 基础 prompt 哈希 + 组合哈希 + 输入哈希 + 输出契约哈希。改任意技能只让受影响任务类缓存失效。

技能三种形态，架构必须都支持：指令型（规则）、知识型（清单/示例）、程序型（固定阶段方法）。只支持前两种，天花板就是"写更好的提示词"。

硬边界：**技能塑造推理，工具改变世界**。技能永不执行副作用，权限与确认留在工具层。

## 5. 待拍板决策

| 编号 | 决策点 | 选项 | 建议 | 决定性理由 | 状态 |
|---|---|---|---|---|---|
| D1 | 谁来选技能 | 声明式 / 模型自主 / 混合 | 声明式 | 模型自选会破坏调用身份、缓存与审计归因；混合仅适用于探索型对话，且选择结果必须回写清单 | 未拍板 |
| D2 | 技能形态 | 纯文档 / 文档 + 机器清单 / 纯代码策略 | 文档 + 机器清单，代码钩子可选 | 可移植、非工程师可维护，又能被编译器确定性处理 | 未拍板（无异议即按建议） |
| D3 | 能力边界 | 仅提示词 / 可声明输出契约 / 可声明程序阶段 | 三者都要，程序阶段固定控制流 | 单轮提示词有天花板；契约提升可靠性；程序阶段才能表达"方法" | 未拍板 |
| D4 | 绑定粒度 | 调用点列技能 / 任务类 + 运行覆盖 | 任务类 + 运行覆盖 | 调用点各自组合必然重新长出口径漂移 | 未拍板（无异议即按建议） |

三个贯穿成败的细节：

1. 技能与数据分离：评估中"检查什么"是数据（criteria），"怎么判断、怎么定级"是技能。
2. 消融是技能准入标准：移除后指标不下降的技能视为提示词膨胀；技能应小而正交。
3. 可编辑但不可变：热编辑只产生新版本，旧版本永久可复现；用户输入永不进入技能层。

## 6. 案例判定：expert-review

逐章映射：

| 章节 | 承载形态 | 单轮 prompt 能承载 |
|---|---|---|
| §0.1 范围解析 | 声明式选择器 | 理论可以，不可靠 |
| §1 锚点 | 必须执行 git | 否 |
| §2 机械取证 | 工具 | 否 |
| §3 分区并行 | 编排 | 否 |
| §4 严重度四维矩阵 | 判断规则 | 是 |
| §5 证据门禁 + 反驳轮 + 自核验 | 程序 + 工具 + 独立上下文 | 否 |
| §6 findings 台账 | 持久状态 | 否 |
| §7 报告模板 | 输出契约 | 是（契约形态） |
| §8 反模式 | 判断规则 | 是 |

九项中只有三项可由提示词承载，其余六项依赖执行语义。

单轮模拟无效的原因：拿不到锚点（报告即无效）、无法执行命令（计数无出处）、无法引入独立代理（反驳轮不成立）、自评自驳违反隔离目的。

阶段不是静态 DAG：反驳轮要对 findings 集合逐个迭代，集合大小由前一步动态决定。执行器至少要支持"固定拓扑 + 有界迭代"。

架构中的正确形态：

| 层 | 承载 |
|---|---|
| 技能层 | §4 判定规则、§8 反模式、§7 报告契约、§0.1 选择器声明 |
| workflow 定义 | 阶段拓扑、有序迭代、各阶段输入输出与门禁 |
| 工具 | 读文件、跑命令、git |
| 子代理 | 无共享上下文的独立复核 |
| 持久状态 | findings 台账、跨轮 carry-over |

结论：expert-review 整体是 workflow，不是 skill。技能层只能承载它的规则与契约。

## 7. 本轮范围分叉

本期是否包含程序型技能：

- 包含 → 需要一个固定阶段执行器（有界迭代状态机，不是 agent 循环），范围显著变大。
- 不包含 → 纯编译 + 校验 + 记账 + 评测，范围干净，但只能表述为"把评审方法注入调用"，不能宣称"可执行 expert-review"。

表述口径必须与范围一致：不建执行器却使用"执行 expert-review"的名义，会让读者误以为证据门禁在生效。
