# ADR-054: Agent 交付流水线与漂移控制闸门

状态：已采纳（2026-11-17，用户拍板）
日期：2026-11-17
前置：ADR-008（compose 三层）、ADR-012（生产拓扑）、ADR-036（PG 迁移版本化）

## 背景

目标是让需求从飞书讨论直接走到上线：群里讨论 → 建任务 → 进入队列 → agent 开发测试 → 合并 → 部署。链路已具备约七成：飞书 webhook 与长连接、copilot 的 `create_task`、任务六态状态机、状态回推、`nightwatch-task-loop` skill、仓库 CI 与 SSM 部署。缺口是四段自动衔接（讨论→任务、队列→执行、测试→PR、部署→回写），以及质量保障机制。

### 核心判断

AI 跑偏不是能力不足，而是**没有代价函数**。人改到某处会不安、删测试会心虚、动 schema 会怕——这些是每一步的代价估算；AI 的代价感知为零，因此持续选择「短期简单、长期代价高」的路径。

由此确立总原则：

> 不给 AI 装直觉，而是把直觉外化成流程里的摩擦点。
> 质量来自**检查点密度**与**闸门硬度**，不来自 AI 的能力。

两条推论：

1. 需要「诚实」的检查不能交给 agent 执行——它能跳过 hook、自评通过、对预算撒谎。
2. 规则数量与执行严格度成反比。只保留少量硬闸，其余降级为建议。

## 适用范围：载体、框架与被管项目

三个仓集合的边界固定，不得混用：

| 类别 | 成员 | 与流水线的关系 | 门禁形态 |
| --- | --- | --- | --- |
| 框架层 | devbie、newbie-modules、newbie-starter、fewbie-starter | 定义契约与工具，不被管理 | PR CI + 人工合并；无 staging、无批次、无候选 |
| 载体层 | nightwatch-backend、nightwatch-frontend、nightwatch-world | 承载队列、调度、通知与部署，作为产品被人类维护 | 常规流程：全量 CI + 迁移演练 + 人工审 + 回滚预案；不进入队列、不参与批次验收 |
| 被管项目层 | client project1、client project2 及后续项目 | 进入队列，按本文全部约束运行 | task PR → dev → 批次 → 候选 → 发布的完整链路 |

- 载体层不进入流水线是结构性要求，不是偏好：流水线坏在合并闸门或批次触发器上时，修复路径不能依赖同一套闸门（自举）；修改 `Task` 表或批次表的任务要迁移正持有在途批次状态的数据库，属于自指修改（状态自噬）；载体故障的影响面是所有被管项目，其检查密度不得低于被管项目（故障域）。
- 载体层的门禁是换形态，不是放宽：自动验收与批次封闭由「每次发布单独演练 + 全量 CI + 迁移演练 + 人工审 + 回滚预案」替代（见「影响」）。
- 载体层发布可能重启 dispatcher、中断在途批次，受约束 18 的排空与恢复语义约束。
- 生产 hotfix 只针对被管项目的生产环境；载体层自身的紧急修复走其常规流程，不作为本流程的例外。

## D0 需求阶段：nw 参与

链路的第一段是「讨论 → 建任务」。这一段原本只靠人，nw 不在场，后果是需求与既有决策的冲突要到开工后才暴露：闸门 1 报 `designRef` 不相关、闸门 2 报越界、验收时才发现 backlog 里已有同项。代价此时已经付出。

D0 把冲突检测前移到讨论阶段。nw 以参与者身份在飞书讨论中在场，**只读**工作区文档，产出一份「需求体检」结论。它不判断需求价值，只做检索与比对——这与「不给 AI 装直觉」一致：文档里有就有，没有就没有，冲突就引原文。

### 输入（只读，覆盖工作区各仓）

| 来源 | 用途 |
| --- | --- |
| `.trae/documents/decisions/**` | 已采纳 ADR 的硬约束与 Status（已采纳 / 被取代） |
| `.trae/documents/specs/**` | 可执行契约：字段、接口、几何映射等可核对条款 |
| `.trae/documents/designs/**` | 概念与实施设计，判断需求是否已有设计 |
| `.trae/documents/backlog.md` | 未完成工程任务，判断是否重复 |
| `.trae/documents/findings.md` | 评审台账，尤其 `open` 项，判断需求是否在踩已知坑 |
| 各仓 `AGENTS.md` | 工作流约定与环境事实（分支、门禁、部署状态） |
| `.trae/skills/**` | 已有操作手册，判断是否只需走既有流程 |
| `packages/modules/**`、`src/modules/**` 目录清单 | 判断是否已有可复用模块，避免重复造 |

### 输出（固定四类，不得自由发挥）

| 类别 | 判据 | 必填证据 |
| --- | --- | --- |
| 矛盾 | 需求与某份**已采纳** ADR / spec 的某条硬约束不可同时成立 | `file:line` + 条款原文摘要 + 二选一处置（改需求 / 走 supersede） |
| 已覆盖 | 已有对应物，分三种：已实现（代码 / 模块已有）· 已决策未实现（ADR / spec 已定）· 已登记未做（backlog 已有条目） | 代码路径 / ADR 编号 / backlog ID，并注明属于哪一种 |
| 建议 | 影响面初判（仓集合、是否触 schema / 契约）、可拆解边界、验收标准草案、相关 `open` finding | 每条指向其依据文档；无依据的不写 |
| 无覆盖 | 文档未涉及，需要人补设计 | 说明已检索范围；不得用通用工程常识补位 |

- **无 `file:line` 的矛盾不进清单**。这是防幻觉的唯一硬判据：nw 可以漏报，不可以编造。
- 建议只写「可拆成 X 和 Y」，不替人决策；拆分权仍归人（D5-2）。
- 「无覆盖」与「矛盾」必须分开：前者该新写 ADR，后者该改需求或 supersede，处置方向相反。
- 「已覆盖」不等于「已实现」：命中已采纳 ADR 或 spec 只说明设计已定，命中 backlog 只说明任务已登记；代码是否已经存在，必须单独标为「已实现」并附路径。

### 参与方式与触发策略

「在场」指事件可见，不是持续发言。分三档，取第二档：

| 档 | 行为 | 取舍 |
| --- | --- | --- |
| 1 点名才答 | 只处理被 `@` 与私聊；群内其他消息丢弃 | 现状，成本最低，但冲突要等人想起它 |
| 2 在场但克制 | 开通群内全量消息读取；被点名（`@` 或文字点名）必回，未点名由模型按文档依据决定是否发言 | **采用**：能看见上下文，又不制造噪声 |
| 3 每句都回 | 每条群消息都调模型并回应 | 不采用：成本与噪声不可控，且与「矛盾必须带证据才发言」冲突 |

实现口径：

- 触发判定放在 lark 模块 `dispatchMessage` 的前置分支，替代当前「群消息无 bot 提及即丢弃」的早退。
- 上下文按 `chatId + thread` 保存最近若干条，否则接不上前文。
- 回复必须节流并设静默窗口；连续发言按噪声处理。

判断分两层，职责不混：

- **点名 → 必回（规则可判）**：`@` 机器人，或文本中出现 nw 的别名（`nw`、`nightwatch`、机器人显示名）。这是唯一由规则直接放行的情形；命中后仍受配额、静默窗口与去重约束，避免连点连回。
- **未点名 → 模型判断**：消息全部送模型，由模型决定是否发言，判据是能否补出文档依据——即四类输出中的矛盾（带 `file:line`）或已覆盖命中。没有依据就沉默。相关性是语义任务，规则只能近似且误差双向：会漏掉「跟之前定的不太一样」这类无关键词的冲突，也会误回「ADR-054 那节我看过了」这类只需确认的消息。因此判断权不在规则。
- **限额由 dispatcher 执行**：每群每小时回复上限、同一 thread 静默窗口、两次回复最小间隔、不回复自己、不重复回复同一条消息。这些可外部执行、模型绕不过，是「AI 没有代价函数」的外部注入，与「诚实自评不交给 agent」不冲突。

「提到某实体」只是特征，不是回复理由。实体指工作区里可被引用的对象：ADR 编号、spec 文件、模块 key、backlog / finding ID、仓名、目录路径、skill 名。命中只说明这条消息在谈工作区里的某个对象，模型据此判断能否补出证据；命中本身不构成发言许可。若引入检索或小模型预筛以降本，只能收缩候选，漏掉的按「不回」处理并计入漏报指标，不得对外称其为判断真源。

平台边界（不通过工程手段补齐）：读不到机器人入群前的历史；没有在线 / 已读状态；语音会议只能经平台转写参与（见「语音会议参与」）；发送有 QPS 限制。验收按上述三档，不按「像真人」验收。

### 语音会议参与

会议里默认旁听：只在被点名时出声，其余情况只发会中文字。

| 能力 | 口径 |
| --- | --- |
| 入会 | 会议中任何参会人均可邀请；入会后只读入会后的转写，读不到入会前的讨论 |
| 输入 | 以平台提供的实时转写文本为准，不假设可获取原始音频；说话人分离质量取决于平台 |
| 未点名输出 | 只发会中文字：命中带 `file:line` 的矛盾或已覆盖结论时发出，否则沉默 |
| 点名输出 | 文字点名或会中点名后允许语音发言；一次会前授权可覆盖本场 |
| 不出声的理由 | 语音打断不可撤销；文字有「不发送」的余量，语音没有 |

落地前置（未实测前不得对外称「已支持」）：

- 机器人能否被邀请入会、是否支持自动入会；
- 实时转写事件是否对第三方应用开放及其延迟；
- 是否允许 TTS 发言、是否受租户配置限制；
- 转写与录音的合规要求与参会人告知；任何人可邀请意味着入会门槛低，入会提示必须对全员可见。

会议中的冲突检测复用同一口径：矛盾必须带 `file:line`，无证据不发言。

### 与人和流水线的衔接

1. 人看体检结论后拍板。需求成立 → 父任务与子任务由 nw 按人确认的内容调用 `create_task` 落库（人可改），nw 不自行决定拆分；`designRef` 可直接取「已覆盖」命中的 ADR，不因「没新写 ADR」而卡住（呼应「被拒绝的方案」中的 `designRef` 条）。
2. 结论随任务落库到 `requirementReview`（可空字段，存报告链接与四类计数），供追溯与闸门 1 读取。
3. 若体检标了「矛盾」而任务未处置（未改需求、未走 supersede、未记 override），建任务时提示一次并留痕；**不阻断**。需求是否成立由人判断，nw 的检索不能成为否决权。
4. 误报率按「矛盾」条目统计（人工判定无效的比例），作为需求侧质量指标记录；连续偏高时收窄检索范围，而不是加规则。

### 能力边界（不声称覆盖）

- 不做需求价值、优先级、可行性判断。
- 不做语义推断式冲突检测：只比对文档条款与需求陈述的字面要素（实体名、字段名、接口路径、状态枚举、路径范围）。
- 需要多段推理才能推出的「间接冲突」不报。
- 不读实现细节，只读模块目录清单；实现层冲突仍由闸门 2 在 PR 阶段抓。

## D1 流水线拓扑

下图只适用于被管项目层；框架层与载体层不进入队列（见「适用范围」）。

```
飞书讨论 / 语音会议（nw 在场：只读工作区文档 → 矛盾 / 已覆盖 / 建议 / 无覆盖，见 D0）
   │  人拍板需求成立 → 建父任务与子任务
   ▼
PENDING 队列
   │  dispatcher 取队首，(repo, module) 加锁
   ▼
git worktree add ../wt-<taskId> -b task/<taskId> origin/dev
   │  agent 在独立 worktree 开发
   ▼
本地快门禁：format / lint / tsc / 单测
   ▼
push task/<taskId> → PR to dev
   ▼
PR CI → 编排器合并队列（同仓串行，squash）→ 合入 dev
   │  每次合入重置 10 分钟静默窗口；窗口到期、合并队列排空且无自动验收在途才构建
   ▼
任务 → TESTING
   ▼
一次构建 → 部署 staging（自动验收模式）→ 自动化端到端回归
   │  本批 = 窗口内合入的 1~N 个任务，条数由窗口决定，不按任务数触发
   │  构建开始即通知飞书：batchBase、批次任务清单、候选选择入口；人决定本批通过后是否进入候选验证
   │  自动验收期间新 task PR 阻塞在合并队列，不进入 dev
   ├─ 不通过：问题定位单元把报错映射到候选任务 → revert 候选提交（定位不了则通知人定回退范围）→ 任务退回 DEVELOPING → 重建重跑
   └─ 通过：本批未被选为候选则放行队列；已被选为候选则直接进入候选验证（暂停队列、dev 锁定、通知人）
   ▼
事件触发开 / 刷新 dev→main PR（每日巡检兜底）
   ▼
候选验证（基准就是当前环境中的这个版本，不重新部署；dev 已锁定，等式成立）
   │  基准就是当前环境中的这个版本，不重新部署
   ▼
全量 CI + 跨仓回归（对同一提交）
   │
   ├─ 失败：修 dev 后出新批次，候选作废，staging 释放回自动验收模式
   └─ 通过：人工验收（唯一一次，覆盖自上次发布以来的全部批次）
        │
        ├─ 人拒绝：问题任务退回 DEVELOPING，候选作废，新批次通过自动验收后可再次启动
        └─ 人确认：触发 dev→main 合并 → 生产部署 → 回灌 dev → 回写 COMPLETED → 解锁
```

约束：

1. **隔离用 worktree，不用分支**。切分支时文件系统仍共享，并行 agent 会互相覆盖未提交文件。worktree 共享 object store，比 clone 快；`node_modules` 不共享，按并行度预留磁盘。
2. **agent 不合并自己的分支**。推分支、开 PR to dev，合并由编排器在 CI 门禁通过后执行。dev 一旦被推红，后续所有任务分支都继承坏代码。
3. **同仓合并串行由编排器维护，不依赖 GitHub merge queue**。当前账号形态（个人账号、私有仓）没有 merge queue：官方口径是「组织拥有的公开仓，或组织 + Enterprise Cloud 的私有仓」，实测 `mergeQueue` 查询返回 `null`、私有仓 rulesets 需 Pro 以上。因此编排器自己维护合并队列：同仓单并发，agent 推分支开 PR 后不自行合并；编排器按序取已通过必需检查的 PR 调 API 合并（squash），合并期间该仓不接受下一次合并动作；跨仓仍并行。批次构建所说的「合并队列排空」即该队列为空且无在途合并动作，用 `GET /pulls?state=open&base=dev` 对账漂移；检查未通过的 PR 不入队，不阻塞批次。不把 GitHub auto-merge 当作合并执行者：没有 merge queue 时它会并发合并，破坏串行。理由：后合的 PR 基线已移动，各自 CI 绿只证明「单独成立」；staging 冒烟发生在合并之后，只能 revert，挡不住坏提交进 dev。
4. **dev 与 main 策略分开**。`main` 人工合并，ruleset 不放宽；`dev` 的 ruleset 要求必需状态检查通过，合并动作由编排器串行执行（见约束 3），不由 GitHub auto-merge 直接合并。
5. **staging 由事件触发，不用定时；批次大小由静默窗口决定，不按任务条数**。每次任务合入 dev 都重置 10 分钟静默窗口；触发条件是「窗口到期 且 合并队列已排空（无待合入 PR、无在途合并）且 无自动验收在途 且 staging 未被候选占用」。窗口到期只表示静默期已满足；队列非空说明还有 PR 在排队合并，此时构建会让批次边界与合入过程重叠（构建期间又合入，批次成员与验收基准随之后移），因此批次封闭以「合并队列排空」为准。触发时捕获批次基准提交 `batchBase = dev HEAD`，此后合入的提交属于下一批并重置下一窗口。窗口计时不受自动验收与队列状态影响，被冻结的只是到期后的构建动作：自动验收结束时窗口若已到期且队列已排空，立即开下一批；否则等到条件满足。窗口内合入 1 个任务就是一个批次，合入 5 个就是同一批次。合入持续不断导致队列长期非空时，批次顺延而不强制切断——这属于合入速率超过 staging 验收吞吐，按限流或人工介入处理。顺序固定：构建 → 部署 → 自动验收。
6. **staging 单环境、两种用途，同一时刻只服务一种**。默认是自动验收模式；被人在批次启动时选为候选的批次，通过自动验收时自动切到候选验证模式并锁定，复用当前部署，不重新部署，自动验收排队。不建第二套环境：两套环境要两批密钥、两套部署与迁移演练，成本高于一次用途切换。
7. **候选验证发生在合并之前，且复用最后一个批次的部署**。dev→main PR 的验证不再单独部署：前置是该批自动验收已通过、当前部署版本等于 dev HEAD；满足后进入验证（候选资格在批次启动时由人选择，通过时自动进入），全量 CI 与跨仓回归跑在同一提交上，通过后人工确认并触发合并。合并后再部署 staging 等于在 main 之后彩排，验收已无法否决合并，只剩回滚。
8. **dev→main PR 由事件开 / 刷新，合并始终人工**。批次启动时向飞书通知（批次基准提交、任务清单、候选选择入口），批次通过自动验收时开或刷新 PR；被选为候选的批次直接进入候选验证并通知人，未选的批次放行队列且不通知；每日巡检只在 dev 领先 main 且无 open PR 时补开，避免事件遗漏造成静默积压。不按时间批量开 PR：批次越大，revert 粒度越粗，归因越难。
9. **候选验证与任务合并互斥，启动即全量锁定**。批次进入候选验证时暂停该仓合并队列（已选择候选的批次在通过时直接进入），dev 不再接受任何新提交；验证失败才解锁、作废候选并把问题任务退回 DEVELOPING。只冻结「新任务排队」不够：任何一次合入都会让 PR 头漂移，确认合并的内容就不再是被验证的那一版。
10. **dev 变红时 revert 优先于修复**。agent 不知道是谁弄坏的，让它修只会开始猜。先恢复绿，再把原任务退回 DEVELOPING。
11. **跨仓任务是串行子任务组**。被管项目（consumer，见「适用范围」；不含载体层）子任务先做（build / lint / 测试 / 验收标准），完成后才允许开工 registry 子任务；后者验收标准为 `diff -rq <consumer>/src/modules/<key> <registry>/packages/modules/<key>` 输出为空。串行由 `dependsOn` 强制，不靠人记。单条子任务仍是「一个 worktree、一条 `task/*` 分支、一个 PR」。
12. **task PR 只做轻量验证，不部署环境**。lint / tsc / 受影响单测 / build；触 schema 时加空库迁移校验，并做启动冒烟（起依赖、启动进程、打健康接口）。全量测试与跨仓组合留到 dev→main。理由：环境数等于并发任务数，每套环境都要复制数据库、迁移与密钥；多个任务共用环境后，验收时「测的是谁」会互相污染。全部 PR 跑全量测试会让 CI 分钟数随 PR 数线性膨胀，所以只跑改动路径覆盖的测试。agent 在开 PR 前须附自证证据：测试输出、构建输出、界面改动截图。
13. **自动验收期 staging 固定在批次基准提交，且新合入阻塞**。部署后 staging 固定在该批次的验收基准提交（触发构建时捕获的 `batchBase`）；自动验收期间新 task PR 阻塞在合并队列，不进入 dev。固定的对象是部署，不是代码：不通过时由 revert 产生新提交，再按新 HEAD 重建，不存在切回旧 commit。
14. **每批构建必须跑自动验收，失败即打回循环**。部署后立即跑端到端回归；不通过 → 问题定位单元给出带证据的候选任务（见「自动验收失败的问题定位」）→ revert 候选提交 → 候选任务退回 DEVELOPING → 修正后重新合入 → 重建重跑，循环直至通过；定位不了就不猜，通知人介入并由人决定回退范围。循环期间合入队列保持阻塞，否则每次重建都混入新任务，失败无法归因。若根因判定在载体层（流水线自身缺陷），终止批次并通知人，不回退项目提交——载体缺陷不能用 revert 项目代码掩盖。
15. **不单独做候选部署；人工验收复用最后一个批次的部署**。批次通过自动验收后 staging 停留在该版本；未被选为候选的批次通过后队列立即放行，下一批启动时再次通知并重新选择；被选为候选的批次在通过自动验收时直接进入候选验证并通知人：暂停合并队列、dev 全量锁定，等式在人取消前一直成立，不设过期自动释放。候选资格绑定批次、不绑定提交：本批自动验收不通过时选择保留，revert 后重建重跑，通过时仍进入候选验证。验证基准就是环境中的这个版本，全量 CI 与跨仓回归跑在同一提交上；进入候选即冻结合并（候选窗口），人确认后由 PR 规则完成 dev→main 合并，否决则候选作废、问题任务退回 DEVELOPING。理由：候选与最后批次本就是同一提交，再部署一次只增加一次构建与版本漂移窗口；人工结论只对最终合入的版本成立，验的必须是环境里那一版。
16. **生产 hotfix 从 main 拉分支，不绕过闸门**。分支起点、验证方式、回灌顺序见「生产 hotfix」小节；紧急度只改变排队优先级，不改变 PR、CI 与人工确认。
17. **发布后回灌 main → dev，回灌完成才算发布结束**。常规发布与 hotfix 同一规则：合入 main 后立即 `git merge main` 回灌 dev，冲突时把发布内容以 cherry-pick 或手工重放落到 dev 并标注来源 commit，禁止改写 main 历史。dev→main PR 的准入检查是 `git merge-base --is-ancestor main dev`（等价于「main HEAD 是 dev HEAD 的祖先」），未回灌即拒绝开或合并该 PR，避免下一次发布把已上线的 hotfix 或发布内容冲掉。回灌提交不是任务合入，不重置静默窗口、不触发批次构建；合并队列保持锁定，直到生产部署与回灌都完成，部署失败时按生产 runbook 处置、处置完成前不解锁。理由：dev→main 的合并方式（merge commit / squash / cherry-pick）都会在 main 上产生 dev 不认识的提交，只在 hotfix 场景回灌会让祖先条件在第一次常规发布后永久为红；把回灌变成每次发布的固定收尾，闸门才有意义。
18. **载体层发布必须排空或可恢复在途批次**。载体发布（部署、迁移、重启）前先进入排空态：停止取新任务、等待在途批次与候选锁落到持久化状态；发布后按持久化状态续跑，未完成批次保留 `batchBase` 与任务清单，不得静默重置。无法排空时（紧急修复）发布后必须人工核对在途批次与队列锁，核对完成前不自动触发新批次。

### 协作形态：免费计划的人员协作与升级差分

2026-11-19 选型：工作区全部仓库在个人账号的免费计划下协作（Team 不再作为目标档位）。免费计划不提供私有仓的分支保护、必需检查、auto-merge 与 merge queue，因此约束 3/4 的强制执行点全部落在编排器与部署守卫上，而不是 GitHub。

| 项 | 免费计划口径 |
| --- | --- |
| 成员接入 | 个人账号私有仓直接邀请协作者（Settings → Collaborators），不共享账号；协作者数量不限，外部合作者同样不计费 |
| 权限 | 开发给 Write，Admin 只留 owner；Write 即可推分支、开 PR、跑 CI |
| 串行合并 | 编排器是唯一合并者，按检查通过顺序调 API squash 合并；不使用 GitHub auto-merge（无必需检查时会并发合并） |
| 防绕过 | 无服务端保护：直接推送 dev / main 只能事后发现——审计 dev / main 上的非 PR 合并提交并告警；`main` 的兜底是 deploy.yml 的 provenance guard，直接推送无法部署 |
| CI 额度 | 2,000 分钟/月按账号共享；用尽默认停机，提额后 $0.008/分钟（Linux 2 核）。约束 12 的受影响测试跑集是硬要求 |
| 凭证 | 生产部署走 OIDC，仓库内不留长期 AWS 密钥；仓库 Secrets 视为对全部 Write 成员可见 |
| 已知风险 | Write 权限可修改 workflow 读取 Secrets；无分支保护意味着越界推送只能事后发现，不能事前阻断 |

若未来升级 Team，只换强制点、不换流程：ruleset 让必需检查与「禁止直推」由 GitHub 强制执行，编排器继续持有队列与合并动作（Team 仍无 merge queue）；席位 $4/人，CI 额度 3,000 分钟/月。当前所有约束必须按免费形态成立，不得假设具备 Team 的服务端保护。

### 验收口径

四个词固定含义，避免混用：

| 词 | 定义 |
| --- | --- |
| 部署批次 | 一个静默窗口内合入的全部任务，对应一次构建、一次部署、一个验收基准提交 |
| 自动验收 | 部署后立即执行的批次级端到端回归；不通过即打回，不进入下一阶段 |
| 发布候选 | 被人在批次启动时选为候选、且已通过自动验收的那个部署；不重新部署，全量 CI、跨仓回归与人工验收都针对它 |
| 验收基准提交 | 触发构建时捕获的 `batchBase`，即部署到 staging 的那个 dev HEAD；候选验证沿用它，不产生新提交 |

- **自动验收每批必跑，失败即打回**。不通过 → 问题定位单元把报错映射到候选任务 → revert 候选提交 → 重建重跑，循环直至通过；定位不了则通知人，不猜对象。循环期间新 task PR 阻塞在合并队列，不进入 dev，否则每次重建都混入新任务，失败无法归因。
- **人工验收只在候选验证中执行一次，且跟随最后一个批次的部署**。批次启动时发飞书通知，人决定本批通过后是否进入候选验证（候选资格绑定该批次）；未选择即通过后放行，不通知。由人在候选验证中一次覆盖自上次发布以来的全部批次；中间被验版本会被后续提交改写，按构建人验的结论必然失效，且人审是链路最贵的环节。
- **候选验证不产生新部署**。候选资格在批次启动时选定，本批通过自动验收时 dev 尚未前进，等式成立并由锁定保持；未选择的批次不进入候选验证——不用旧版本验证，也不为验证再构建一次。进入候选即暂停合并队列，验证期间 dev 不再前进。
- **批次大小由静默窗口决定，不设固定条数**。触发条件是「窗口到期 且 合并队列排空」，不是「攒够 N 个任务」；窗口内只合入 1 个就验 1 个，合入 5 个就一起验 5 个，没有上限。
- **正常流程不切 commit、不重建**。一个批次部署一次；只有失败打回时由 revert 产生新提交并重建。
- **人工确认即合并触发**。人点击确认后由 PR 规则完成 dev→main 合并，随后生产部署、回灌 dev 并解锁；否决则候选作废、问题任务退回 DEVELOPING，等下一批启动时重新选择候选。
- **归因依据是验收标准与提交区间，不是代码隔离**。失败先由问题定位单元把报错映射到候选任务；定位不了转人工，由人看批次区间决定回退范围。只在组合时才出现的缺陷，批量部署无法归因，这是已知代价。根因判定在载体层时终止批次并转人工，不回退项目提交（见约束 14、18）。

### 候选入口：批次启动时选择

`dev HEAD == 部署版本` 只在批次刚部署完、dev 尚未前进时成立。活跃流水线会在最后一次合入 10 分钟后开下一批并覆盖 staging，事后启动候选验证时等式往往已不成立（R11-04）。因此把选择点前移到批次启动：**批次一开始构建就发飞书通知，人决定本批通过后是否进入候选验证**；选择绑定这个批次，不存在「事后补启」的路径。

| 项 | 口径 |
| --- | --- |
| 通知 | 批次构建开始时推送飞书消息：批次基准提交 `batchBase`、本批任务清单、候选选择入口（进入 / 不进入） |
| 选择 | 人在本批自动验收通过前选择「进入候选验证」；未选择即视为不进入，不阻塞自动验收 |
| 进入验收 | 已选择且本批通过自动验收时，不放行合并队列、不构建下一批，暂停队列并锁定 dev，staging 停在验收基准提交，同时通知人（提交、批次任务清单、验收入口） |
| 验收 | 人在候选验证中执行全量 CI、跨仓回归与人工验收；等式已由锁定保证，不再有人工卡点 |
| 取消 | 只有人显式取消才释放：清除选择、放行队列、staging 回自动验收模式并通知；不设过期自动释放 |
| 失败 | 本批自动验收不通过时选择保留，走问题定位与打回循环；修复后通过（同一批次重建）仍进入候选验证 |
| 冲突 | hotfix 抢占候选锁时选择作废并通知人；候选验证进行中不再接受批次构建 |
| 权限 | 任何能登录 nightwatch 的用户都可以选择、取消与释放，不设专人审批 |

- **选择只决定「批次通过后是否放行」**，不改变自动验收、问题定位与打回规则。
- **事后不补启**：批次通过后 dev 已前进或下一批已启动，等式不再成立；错过通知即等下一批的通知重新选择。
- **不设过期窗口**：选择是人确认发布计划后的动作，环境停在该批次上等待验收是预期状态，不是需要回收的异常；释放只由人显式取消或 hotfix 抢占触发。
- **停机成本由人承担**：候选验证期间流水线不前进，计划变更时人必须取消，否则后续任务全部阻塞在合并队列。

### 自动验收失败的问题定位

自动验收失败时，先定位再打回。定位由独立的「问题定位」单元执行；它是 agent，输出是**假设**，不是结论：

| 项 | 口径 |
| --- | --- |
| 输入 | 失败用例名、错误日志、堆栈、接口路径、页面路由；本批每个 task PR 的提交 diff、`scopePaths`、`acceptanceCriteria` |
| 判据 | 由模型判定：只有报错中的文件 / 符号 / 路由与本批某任务的 diff 有**可指出的交集**才算候选；交集须附 `file:line` 或日志片段 |
| 输出 | 候选任务集合（含证据）或「无法定位」；不得输出无证据的猜测 |
| 处置 | 有候选：revert 候选提交 → 候选任务退回 DEVELOPING → 重建重跑；无法定位：不猜、不回退，保持合并队列阻塞与 staging 占用，通知人介入 |
| 上限 | 同一批次连续两轮定位仍失败即强制转人工，由人决定回退整个批次区间 |

- **定位失败不等于没有责任人**。它只说明证据不足以指向单提交；此时由人看批次区间决定回退范围，agent 不得自行扩大 revert 范围。
- **误判的代价是一次重建**。定位错的候选被 revert 后，下一轮仍失败，按上限转人工；不因为一次误判就改判整批。
- **定位单元不修问题**。它只回答「最可能是哪几个任务」，修复仍回到对应任务的 DEVELOPING 循环。

### 生产 hotfix

线上缺陷不走批次，但也不绕过闸门。分支从 `main` 拉，不从 `dev` 拉：

```
main → hotfix/<taskId> → PR to main（全量 CI + 闸门 2/3）→ 抢占 staging 候选锁，部署 hotfix 提交
   → 冒烟 + 回归 + 人工确认 → 合并 main → 生产部署 → 回灌 dev → 恢复批次流水线
```

- **起点是 main**。从 dev 拉会把未发布的批次带进 hotfix，也无法保证分支只含修复。
- **闸门不降级**。仍走 PR 与完整 CI，ruleset 不放宽，禁止直接 push main；闸门 2/3、预算照常；任务必须登记，`SIMPLE` 可不写 `designRef`，但 `acceptanceCriteria` 与 `impact` 必填。触 schema 的 hotfix 必须带迁移文件并走 `migrate deploy`，与常规发布同一条路径。
- **staging 显式部署一次**。hotfix 的提交不在 dev 上，无法复用批次部署，这是「候选验证不产生新部署」的唯一例外：按候选验证的方式拿锁（暂停合并队列、暂停批次部署），部署 hotfix 提交并跑冒烟与回归，结束后释放。
- **人工确认不可省**。hotfix 直接进生产，人是唯一的语义闸门；agent 只负责实现与自证，不能合并 main，也不能触发生产部署。
- **回灌先于恢复**。与常规发布同一条规则（约束 17）：hotfix 合入 main 后立即回灌 dev，未完成回灌前不解锁、不恢复批次流水线；dev→main PR 的祖先检查会拒绝任何未回灌的发布。
- **待验版本作废**。回灌后 dev HEAD 已变，staging 上待验的批次作废，释放锁后按新 HEAD 重新构建、重新走自动验收。
- **多个 hotfix 串行**。同一时刻只允许一个 hotfix 在验证或合并，避免 main 连续漂移与回灌冲突。

## D2 任务模型

| 层级 | 角色 | 产物 | 状态来源 |
| --- | --- | --- | --- |
| 父任务 | 设计单元 | `designRef` + 验收标准 + 子任务拆解 | 由子任务派生，不进六态状态机 |
| 子任务 | 执行单元 | 一个 PR | 六态状态机 |

字段：

| 字段 | 用途 | 约束 |
| --- | --- | --- |
| `parentId` | 指向父任务 | 可空；非空即不可直接开工 |
| `designRef` | 设计真源引用 | `DESIGNED` 任务必填；子任务默认继承父任务 |
| `acceptanceCriteria` | 验收标准 | **开工前必填**（闸门 1） |
| `scopePaths` | 允许改动的路径集合 | glob；同时是准入判据的计量对象；开工后冻结 |
| `impact` | 影响面声明（`repos` / `touchesSchema` / `touchesContracts` / `irreversible`） | 建任务时填写；开工后冻结；闸门 2 校验声明与实际一致 |
| `changeClass` | `SIMPLE` / `DESIGNED` | 由 `impact` 与 `scopePaths` 推导，不存人工声明 |
| `dependsOn` | 前置子任务 | 非空且未全部 COMPLETED 即不可开工 |
| `sourceRef` | 来源讨论（chatId + messageId） | 可空；用于澄清时回读原文 |
| `blockedReason` | 阻塞原因 | 转 BLOCKED 时必填 |
| `designRefJustification` | 说明本次改动为何落在 `designRef` 覆盖范围内 | `designRef` 相关性无法机械判定时必填（闸门 1 触发 BLOCKED 后由人补齐） |
| `requirementReview` | 需求体检结论（报告链接 + 矛盾 / 已覆盖 / 建议 / 无覆盖 四类计数） | 可空；由 nw 在讨论阶段写入，人可编辑；不作为闸门 1 判定项 |

状态机新增 `BLOCKED`：

| 流转 | 触发 |
| --- | --- |
| `PENDING → BLOCKED` | 闸门 1 拒绝（缺 `designRef` / `acceptanceCriteria` / 依赖未完成） |
| `DEVELOPING → BLOCKED` | 闸门 2/3 停手、闸门 4 触发、需人工澄清 |
| `BLOCKED → DEVELOPING` | 人补齐准入条件或 reset 计数器后恢复 |
| `BLOCKED → CANCELLED` | 人放弃该子任务 |

## D3 准入判据

判定分三段：声明 → 推导 → 复检。

**声明**。任务创建时携带 `impact`，由设计阶段（父任务或人）填写，不由 agent 从描述推断：

| 子字段 | 语义 | 复检方式 |
| --- | --- | --- |
| `repos` | 预期改动的仓 | 实际改动仓集合 ⊆ `repos` |
| `touchesSchema` | 是否动 `prisma/schema.prisma` 或迁移 | 实际路径命中 schema / `migrations/` 却未声明即失败 |
| `touchesContracts` | 是否动跨模块 / 跨仓契约（DTO、SPI、事件） | `designRef` 列出契约文件清单，命中却未声明即失败 |
| `irreversible` | 是否含不可逆操作 | 执行器边界命中时比对声明，未声明即停 |

**推导**。`changeClass` 是纯函数：

```
DESIGNED iff repos.length > 1
         || touchesSchema
         || touchesContracts
         || irreversible
         || scopePaths.length > 20
```

否则 `SIMPLE`。计量对象是设计阶段填写的 `scopePaths` 条数；不得用实现完成后的 diff 文件数（事后量会破坏准入语义），实际文件数只由闸门 2 约束。

**冻结**。`impact` / `scopePaths` / `changeClass` 在 `PENDING → DEVELOPING` 时冻结。此后的修改只能由人通过 override 通道执行并留审计记录，agent 无写权限。

**复检**。声明错误由闸门抓：实际仓集合 ⊄ `repos`、实际路径 ⊄ `scopePaths`、或命中 schema / 契约清单却未声明 → 闸门 2 停手并附差异清单；同一子任务连续 2 次触发计入闸门 4。

`DESIGNED` 必须有 `designRef`，但允许指向**已有** ADR——引入新决策才需要新写 ADR。引用的 ADR 必须覆盖本次改动：其「影响」或 Cross-host check 声明的仓集合须与 `impact.repos` 相交，否则闸门 1 转 BLOCKED。`SIMPLE` 免 `designRef` 校验，但不免 `impact` 声明。

## D4 闸门

| # | 闸门 | 判定点 | 判定者 | 失败后果 |
| --- | --- | --- | --- | --- |
| 1 | 开工准入 | `PENDING → DEVELOPING` | 服务端状态机 + dispatcher 预过滤 | 拒绝流转，转 BLOCKED 并通知 |
| 2 | 改动范围 | 提交前 · PR CI | dispatcher 本地（快失败）+ CI（权威） | 停手，退回 DEVELOPING，附差异清单 |
| 3 | 测试不弱化 | PR CI | CI job（AST 提取） | PR 红，阻断合并 |
| 4 | 预算 | 全程持续 | dispatcher 计数器 | 杀会话，转 BLOCKED，`blockedReason` 写明触发项 |
| 5 | 能力边界 | 命令执行瞬间 · 环境构建时 | 命令代理 + 环境构建 + 出站白名单 | 命令被拒 / 环境不可用 |

### 闸门 1：开工准入

判定规则，全部满足才允许流转：

1. `DESIGNED` 任务有 `designRef`，且该引用**可解析、状态为生效、未被取代**（语义与 `adr-placement` 的 Status 定义一致）。
2. `acceptanceCriteria` 非空。
3. `parentId` 为空；`dependsOn` 全部 COMPLETED。
4. `impact` / `scopePaths` 合法（`scopePaths` 非空、不含禁止路径、不超 20 条）。
5. `designRef` 与本次改动相关：ADR 的「影响」或 Cross-host check 声明的仓集合与 `impact.repos` 相交。无法机械判定时转 BLOCKED，待人补齐 `designRefJustification` 后放行。

子任务 `designRef` 默认继承父任务；显式声明不同者，`changeClass` 不得为 `SIMPLE`。

D0 的需求体检结论不参与闸门 1 判定；`requirementReview` 存在未处置的矛盾时，只提示并留痕，不阻断流转。

### 闸门 2：改动范围

改动集合取自 `git diff --name-status -M <base>...HEAD`，rename 与 delete 均在视野内；删除或重命名必须在 `impact` 中显式声明。

匹配规则：

- `scopePaths` 为 glob，支持 `dir/**`；本地与 CI 共用同一实现函数，禁止两层各写一份。
- 空集合建任务即失败。禁止仓根级通配（`**`、`*`、`src/**`），每条必须落在模块或应用目录内。
- 豁免项：lockfile、`dist/`、构建缓存、快照目录；`migrations/` 不豁免。
- **禁止路径清单**（框架级下限，宿主只能追加不能删减）：`.github/workflows/**`、`.github/actions/**`、`deploy/**`、`tools/gates/**`、`.trae/skills/**`。任何 `scopePaths` 包含之，建任务即失败。清单同时是**合并闸**：编排器在调合并 API 前读取 PR 改动路径（`pulls.listFiles`），命中 `.github/**` 或 `deploy/**` 即拒绝合并并告警；只靠建任务期校验不够，免费计划没有 ruleset，agent 可在 PR 内改工作流文件。
- **闸门实现位置**：路径匹配函数与禁止路径清单常量由编排器持有（`src/application/task-pipeline/**`，不落入被管项目的 `scopePaths`）；闸门 3 的 AST 判定器随载体层可复用工作流走（`nightwatch-backend/.github/workflows/verify.yml`，`on: workflow_call`）；被管项目只保留 thin caller（`.github/workflows/task-pr.yml`，`uses:` 钉全 SHA），该文件对 agent 只读（见跨闸通则第 5 条）。被管仓必须在 Actions 设置中把 access level 设为 `user`，否则 caller 静默失败——没有 check 即 fail-closed，不会误放行，但会表现为队列永久为空，需纳入巡检。
- **目录归属**：这套流程是 nw 的应用能力（载体层产品功能），不是框架层资产，与 newbie-starter / fewbie-starter 无关——starter 只是客户项目自己的骨架来源，流程不持有也不分发客户仓骨架。整套资产都归载体仓所有：编排器（`src/application/task-pipeline/**`）、闸门工作流、闸门脚本、写入客户仓的 caller。物理位置只受一条 GitHub 硬约束限制：可复用工作流必须位于 `.github/workflows/`，故闸门体是 `.github/workflows/verify.yml`；**闸门脚本内联在 `verify.yml` 自身**（here-doc 写出后执行），不放在载体 `scripts/` 再按 SHA 取出——客户端仓的 `GITHUB_TOKEN` 只能读自己，跨仓检出载体需要额外凭证，而任何发给客户仓的只读 PAT 都会被 Write 成员（含 agent）经 Secrets 读到，等于把载体源码开放给被管项目。内联让「被管项目只持有一个 caller」成立，且没有任何需要保活的跨仓读取；代价是脚本不能单测，用 `node --check` 与实跑取证（见更新记录）。thin caller 的内容由应用域持有并在接入时渲染写入客户仓，不存副本，漂移以「重渲染后 diff」检测。客户仓里由本流程写入的文件只有 caller 一个。

次要判定：改动行数（add + del，排除豁免与生成物）超过 300 → 不按越界处理，记 D6 违规并通知人。

### 闸门 3：测试不弱化

四条规则同时执行：

1. **有效断言**计数不得下降。有效 = 非弱断言、且位于可达分支。基线固定为 PR 的 base sha。
2. 新增禁用标记数必须为 0：`skip` / `only` / `todo` / `xit` / `xdescribe` 及同义标记。
3. 弱断言净增不得为正。成员判据固定为：`toBeTruthy` / `toBeFalsy` / `toBeDefined` / `not.toBeNull` / `not.toBeUndefined` / `not.toThrow` / `toEqual(expect.anything())` / `toMatchObject({})` / 单独使用的 `expect.any(...)`；清单可由配置追加，不可删减。
4. 不可达断言净增必须为 0：断言节点的祖先链存在字面量恒假条件（`if (false)`、`while (false)`、`&&` / `||` 死分支）即计入。

口径：计数由 AST 提取，不用正则；参数化 / 表驱动测试按用例实例计数，注释掉的代码不计入。

能力边界（不声称覆盖）：从未被调用的 helper 内断言、跨文件死代码、弱断言的语义等价替换（如精确匹配改为范围匹配）无法静态判定。这些不做阻断，由覆盖率信号与人工验收兜底；实现时不得把这些计为「已防」。

合法的测试删除只能走 override（人工、留原因）；PR 内无法自证删除正当。

### 闸门 4：预算

| 计数器 | 阈值 | 计量口径 |
| --- | --- | --- |
| 同类失败 | 连续 2 次 | 指纹 = `hash(闸门编号 + normalize(错误输出))`；normalize 去除时间戳、UUID、绝对路径、行列号；不同闸门不互相累计 |
| 累计改动 | 单子任务 > 600 行 | add + del；排除项按**路径白名单**判定，不按文件名匹配 |
| 墙钟 | 单子任务 > 45 分钟 | 有效执行时间，不含模型排队与 CI 等待；允许 1 次人工续期 |
| 提交次数 | 单子任务 > 3 次 push | 含 force-push；rebase 不计入 |
| 无进展 | 连续 10 次工具调用无文件变更 | 与墙钟互补，捕捉「反复读文件、重跑同一命令」 |

任一触发 → 杀会话、转 BLOCKED、通知人。计数器由 dispatcher 持久化，跨会话与 agent 重启不重置，只有人显式 reset 才清零；agent 不可读写。

dispatcher 记录每次触发的实际分布（含模型 token 成本），首月按真实数据回填阈值。调整时改 dispatcher 常量，不改本 ADR。

### 闸门 5：能力边界

前提不变量：**闸门 5 依赖闸门 2 的禁止路径清单**。agent 若能改流水线或部署脚本，命令代理形同虚设。两者缺一即视为闸门 5 未闭合。

- **命令代理采用 allow-list**，最小集：构建 / 测试 / lint / 只读 git / 向 `task/*` push。其余一律拒绝并记录。deny-list 不作为主闸（`sh -c`、管道、编码执行均可绕过）。
- **git 凭证**：单仓 + `task/*` 分支前缀限权；代理层按 refspec 拒绝向 `dev` / `main` 的 push 与 force-push，不依赖 ruleset。
- **依赖安装**固定 `--ignore-scripts`，依赖在镜像内预装（否则放行 registry 即等于任意代码执行）。
- **环境变量白名单**：不注入生产 `DATABASE_URL`、不挂 `/root/.aws`、不注入 SSM / S3 写权限、不持有宿主 docker socket。生产连接串与云凭证在构建期就不可达，不做运行时判断。
- **出站白名单**作纵深。
- 因成本保留凭证挂载或 docker socket 时，必须**显式声明闸门 5 未闭合**，不得宣称有闸。

### 跨闸通则

1. **fail-closed**：判定异常、被跳过、超时，一律按「未通过」处理并阻断流转。禁止实现为放行。
2. **闸门自保护**：判定实现不落在被管项目内——路径匹配函数与禁止路径常量由编排器持有（`src/application/task-pipeline/**`），闸门 3 的 AST 判定器随载体层可复用工作流走（`on: workflow_call`）。被管项目只保留 thin caller，其 `uses:` 必须钉全 SHA，该文件对 agent 只读；合并前以 `pulls.listFiles` 拒绝触碰 `.github/**`、`deploy/**` 的 PR。修改闸门代码只能走载体层人工 PR。
3. **override**：五闸都提供人工豁免通道，仅人可执行，必须记录原因、范围、有效期并写入审计日志；只放行当次，不改变计数器语义。
4. **短路与累计**：任一闸失败即停手，不继续消耗预算；同一子任务同一指纹连续 2 次失败计入闸门 4。
5. **检查名契约与 caller 不可伪造**：跨仓复用工作流的 check 名由 GitHub 组合为 `<caller job> / <called job>`（2026-11-19 实测组合规则；spike 中 job id 为 `gate`，故测得 `verify / gate`）。生产契约定为 `task-pipeline / task-pr`——caller 侧 job id 固定命名 `task-pipeline`（标明归属，且不与客户仓自己的 `verify` job 撞名），被调用 workflow 的 job id 固定 `task-pr` 并显式写 `name: task-pr`（不依赖 id 隐式作为显示名）；两个名字都由载体渲染/持有，客户端不改。裸 `task-pr` 永不命中，`TASK_PIPELINE_REQUIRED_CHECKS` 必须写组合名。同一 check 名可被被管项目内一个普通 job 伪造：同名、同 `github-actions` app、`details_url` 同指 caller 仓，check run 层面无法区分。因此判据必须是「必需名通过 **且** PR 未触碰 `.github/**`、`deploy/**`」，路径排除是这条闸门的承重墙，不是加固项。复用工作流的引用必须钉全 SHA，不用移动 tag。

## D5 硬约束

1. **agent 不得自证验收**。CI 绿只证明能编译、测试能过，不证明实现了验收标准。验收标准由人写、验收由人做，agent 只提供证据。
2. **agent 不得自行拆任务**。它只能报告「建议拆成 X 和 Y」，拆分权留给人。
3. **agent 不得自行调整工作顺序**。队列由人排序，agent 只做队首。
4. **禁止用 agent 自评 / 写复盘来控制漂移**。同一模型判断自己有没有跑偏，与判断代码对不对是同一个自证循环。

## D6 检查点密度

决定成败的参数是**两次人工检查之间 agent 能做多少事**，漂移累积与无人看管时长成正比。

子任务粒度：一个 agent 会话能做完，人能在一屏 diff 内看完。阈值：一次子任务 = 一个 PR = 一处逻辑变更 = diff 300 行以内，超出继续拆。该阈值由闸门 2 的次要判定**观测**：超出只记 D6 违规并通知人，不阻断合并。

## 被拒绝的方案

| 方案 | 拒绝理由 |
| --- | --- |
| agent 直接推 dev、自行合并 | dev 反复变红并连锁污染后续分支；合并权必须留在门禁 |
| 只切分支不做 worktree 隔离 | 文件系统共享，并行 agent 互相覆盖未提交文件 |
| 定时 cron 轮询触发 staging 部署 | 白跑构建、反馈延迟不可控 |
| 每个大任务强制新写 ADR | 撞上 ADR 定稿封存约束，产生假 ADR 与编号膨胀；改为 `designRef` 可引用既有 ADR |
| 把验收也自动化 | 链路退化为自证循环，跑得越快错得越远 |
| 用更多规则覆盖全部风险 | 规则一多，人记不住哪个是真闸，agent 开始「通过检查」而非「做对事」 |
| 跨仓拆成两个独立父任务 | 丢失串行依赖与验证证据链 |
| registry 子任务重跑全套验证 | 违反 registry 既有约定，且证明力弱于 `diff -rq` 字节一致 |
| 从任务文本推断影响面 | 语义推断不可求值；改为显式声明 + 闸门复检 |
| 只靠 ruleset 兜底破坏性操作 | 不覆盖非 git 破坏性路径，属虚假保证 |
| 用 deny-list 作命令代理主闸 | `sh -c`、管道、编码执行均可绕过 |
| 按文件名排除生成物 | agent 可把代码写进 `*.generated.ts` 绕过行数预算 |
| 用正则数测试与断言 | 注释、条件编译、参数化测试均可骗过 |
| 只防测试数下降 | 加 `skip`、降断言强度即可让测试失效而数量上升 |
| 让 agent 自己写 override 记录 | 等价于取消闸门 |
| 用 nw 的需求语义判断决定需求是否成立 | 需求价值没有可验证真源，判断无法复核，且与「不给 AI 装直觉」冲突；改为只报文档冲突，价值判断留给人 |
| 把需求体检做成建任务的硬闸 | 检索有漏报，硬闸会把正确需求挡在门外；正确位置是讨论阶段的建议，矛盾未处置时只提示留痕 |
| 用关键词或规则决定「这条要不要回」 | 相关性是语义判断，规则双向误判：漏掉无关键词的冲突，误回只需确认的消息；改为点名硬触发 + 模型判相关性，规则只管限额 |
| 会议中主动语音插话 | 语音打断不可撤销，多人会议的噪声代价高于文字；改为默认旁听、点名才出声 |
| 同仓 PR 并行合并，只靠 staging 兜底 | 冒烟发生在合并之后，只能 revert；后合 PR 的基线已移动，各自 CI 绿不等于组合绿；改为同仓合并串行 |
| dev→main PR 合并成功后再部署 staging | 验收位于合并之后，已无法否决合并，只剩回滚；staging 退化为生产之后的第二次彩排；改为候选态在合并前部署验收 |
| 定时开 dev→main PR | 时间驱动会把不相关批次塞进同一个 PR，revert 粒度变粗、归因变难；改为验收通过时事件触发，每日巡检只补开缺失的 PR |
| 为发布候选单建一套 pre-prod | 两套环境要两批密钥、两套部署与迁移演练，成本高于一次用途切换；改为 staging 单环境双用途，候选验证优先、自动验收排队 |
| 每个 task PR 部署一套全栈预览环境 | 成本约为服务数 × 打开 PR 数，且每个环境都要复制数据库、迁移与密钥；选择性预览依赖请求路由设施，我们不具备；改为 PR 只做轻量验证，环境验证放在合并后 |
| 验收时切到每个任务的提交单独构建 | 构建次数等于任务数，且该提交不含同批次其他改动，验证不到组合；改为一次部署、整批自动验收 |
| 每次构建后都安排人工验收 | 人工结论只对最终合入的版本成立，后续提交会改写被验版本；且人审次数等于构建数，链路瓶颈前移；改为每批必跑自动验收、人工只在候选验证中验一次 |
| 为候选验证再部署一次 | 候选与最后一个批次是同一提交，重复部署只多一次构建与一次版本漂移窗口；改为进入候选时复用当前部署，版本由批次启动时的选择锁定 |

## 影响

- **nightwatch-backend**：`task-management` 加字段（`parentId`、`designRef`、`acceptanceCriteria`、`scopePaths`、`impact`、`changeClass`、`dependsOn`、`sourceRef`、`blockedReason`、`designRefJustification`、`requirementReview`）与 `BLOCKED` 状态，需迁移；`task.service` 实现闸门 1 的流转校验并调用闸门判定；路径匹配函数、禁止路径清单与闸门 3 的 AST 判定器实现于 `tools/gates/**`（禁止路径，agent 不可改）；新增 PR CI job（闸门 2 复检、闸门 3 AST 判定、闸门自保护，执行 base sha 版闸门代码）；task PR 的 CI 只跑受影响测试、构建，触 schema 时加空库迁移校验与启动冒烟，不部署环境；全量测试与跨仓组合由 dev→main PR 的 CI 承担，该 PR 的准入额外校验「`main` HEAD 是 `dev` HEAD 的祖先」（`git merge-base --is-ancestor`），且每次发布（含 hotfix）后必须先回灌 dev 才解锁，未回灌的发布会被拒绝；`deploy.yml` 的 provenance guard 同时接受 `dev` 与 `hotfix/*` 的合并来源，并增加部署成功回调与任务回写，支持 staging 两种用途的切换与占用状态（含批次启动通知与候选选择、通过后自动进入候选、显式取消与 hotfix 抢占候选锁）；自动验收失败时运行问题定位单元（读取失败用例、日志与批次 diff，输出带 `file:line` 的候选任务；定位不了通知人）；copilot 增加需求体检工具（只读检索 D0 所列文档，按四类结构输出，矛盾条目强制带 `file:line`）；lark 模块的群消息触发改为点名必回 + 未点名由模型按文档证据判断是否发言（全量可见；上下文按 `chatId + thread` 保存；配额与静默窗口由 dispatcher 执行）；接入会议转写，默认旁听，点名才出声，其余情况只发会中文字。

- **worldzhy-knowledge**：`nightwatch-task-loop` skill 改为执行器调用约定，删除「靠人检查 git status 做并行互斥」的失效条款；补 D0 需求体检的触发时机与四类输出口径。
- **newbie-modules**：`task-management` 的结构变更随 registry 走 back-port；back-port 段补充 registry 子任务验收口径（`diff -rq` 为空、不重跑测试）。
- **载体层与被管项目层的分工**：上述 nightwatch-backend / nightwatch-frontend 改动是载体层自身的常规开发交付（人类 PR + 全量 CI + 人工合并 + 发布演练，不进入队列、不参与批次验收）；被管项目（client project1/2）通过装配 `task-management` / `github` / `lark` / `task-pipeline` 获得同一语义，各自持有队列、staging 与凭证，不共享数据库。

## 待决

1. ~~**dev 分支的 ruleset 是否开放自动合并**~~。已于 2026-11-17 决议：开放，见更新记录。2026-11-19 修订：合并动作改由编排器执行，GitHub auto-merge 不作为执行者。选型改为免费计划后，私有仓无法配置必需状态检查，该前提改由编排器读检查结果承担（见「协作形态」）。
2. ~~**staging 环境尚未搭建**~~。已于 2026-11-19 决议：新申请一台与 prod 同规格的 EC2 作为 staging；环境补齐前该段空转。
3. ~~**CI 分钟数成本**~~。任务级 PR CI 的跑数等于任务数，需压到最小集合，否则可能比模型调用更贵。2026-11-19 决议：额度用尽后加购，不引入 self-hosted runner——额度按账号计（免费计划 2,000 分钟/月，不随协作者数量增长），私有仓 Linux 2 核超量 $0.008/分钟；因此约束 12 的轻量跑集必须保留，不能用「每个 PR 跑全量」换便利。
4. ~~**GitHub merge queue 的可用性**~~。已于 2026-11-19 决议：不可用，改由编排器维护合并队列（见约束 3 与更新记录）。核实依据：`mergeQueue` 查询在三仓均返回 `null`；私有仓 rulesets API 返回 403（需 Pro 及以上）；官方口径为「组织拥有的公开仓，或组织 + Enterprise Cloud 的私有仓」。选型改为**免费计划**（个人账号私有仓，协作者与席位不计费）：不购买 Team，私有仓分支保护与必需检查均不可用，串行合并、检查判读与防绕过全部由编排器与 deploy guard 承担（见「协作形态」小节）。落地前置：新增 task PR → dev 的 CI 工作流（当前 CI 仅在 PR→main 触发）、编排器实现串行合并与队列空态查询、对 dev / main 的非 PR 合并提交做审计告警。
5. ~~**staging 用途切换的占用与回收**~~。已于 2026-11-19 决议：任何能登录 nightwatch 的用户都可以选择候选、取消与释放，不设专人审批；入口随批次通知与候选通知提供；不设过期自动释放，释放只由人显式取消或 hotfix 抢占触发。
6. ~~**界面类任务是否单开按需预览环境**~~。已于 2026-11-19 决议：不做，统一走合并后的 staging 验收，不预留按需预览的设计位。
7. **候选验证锁的原子性**。候选入口收敛为批次启动时的选择后，不存在「事后启动」与构建竞争的路径；仍需保证「批次通过自动验收」到「暂停队列 + 锁定 dev + 通知」是一次原子状态迁移，避免与放行竞态；人工确认前再校验一次 HEAD 未变，再触发合并。
8. ~~**问题定位单元的实现与成本**~~。已于 2026-11-19 决议：直接接模型——失败用例、日志、堆栈、接口 / 页面路径与本批 diff 一并交给模型判定；输出仍必须是带 `file:line` 或日志片段证据的候选集合或「无法定位」，模型不得只给猜测；定位不了转人、连续两轮转人的规则不变。定位失败率、误判率与单次成本作为指标记录，用于判断该环节是否值得保留。

## Cross-host check

| 维度 | 框架 / registry 层 | 宿主层 |
| --- | --- | --- |
| 任务模型 | `task-management` 提供父子层级、`designRef`、`scopePaths` 等通用字段与状态校验 | 宿主不得私自扩展字段语义；项目 / 应用绑定由宿主提供 |
| 闸门 | 闸门接口与判定语义通用（拒绝、停手、退回流、fail-closed）；禁止路径清单的框架级下限不可覆写 | 宿主只能**追加**禁止路径，不能删减框架级下限；命令白名单、模块锁粒度、CI job 内容由宿主决定 |
| ADR 准入 | `designRef` 允许指向任意既有决策文档，不绑定目录格式；相关性由闸门 1 校验 | 宿主按 `adr-placement` 决定决策文档归属仓 |
| 流水线拓扑 | 不定义；dev / staging / main 属于部署形态 | `main` 人工确认后合并、`dev` 在必需状态检查通过后由编排器串行合并、staging 事件触发部署且以合并队列排空为批次封闭条件、单环境双用途（自动验收 / 发布候选优先）、候选入口（批次启动时选择、通过即自动进入候选验证、无过期释放），均为宿主策略 |
| 被管对象范围 | 不定义；哪些仓进入队列由宿主声明 | 被管项目集合是宿主配置；框架层与载体层永不进入队列，此边界不可由宿主放宽 |
| 需求体检 | 报告四类结构与「矛盾须带 `file:line`」通用；`requirementReview` 字段语义通用 | 检索哪些仓的文档、飞书接入方式、误报率统计口径由宿主决定 |
| 会议参与 | 触发分层通用：点名才出声、其余只发文字；无 `file:line` 不发言 | 入会方式、实时转写接入、TTS 权限与合规告知由宿主决定 |
| 可移植性 | 任意宿主装配同一模块即获得相同的准入与闸门语义 | 分支保护、CI 计费、执行器形态是 nightwatch 特有 |
