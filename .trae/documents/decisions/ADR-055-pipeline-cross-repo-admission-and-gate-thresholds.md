# ADR-055: 交付流水线的跨仓形态、准入语义与闸门阈值补正

状态：已采纳（2026-11-17，用户指示修复 round8 评审 P1）
日期：2026-11-17
补正：ADR-054。本 ADR 取代其 D1 的跨仓形态缺位、D3 全文、D4 的闸门 4 与闸门 5 两行；ADR-054 其余决策（D2、D5、D6 及 D1 的 worktree 隔离、合并策略、staging 触发、revert 优先）继续有效。
前置：ADR-054（交付流水线与漂移控制闸门）、ADR-012（生产拓扑）、ADR-036（PG 迁移版本化）

## 背景

round8 评审（`.trae/documents/reviews/expert-review-2026-11-17-round8.md`）对 ADR-054 拆解 8 条主张，判定 3 成立、3 部分成立、2 不成立，其中 5 条 P1 全部落在「判断到可执行机制的落点」：

- R8-03：D1 的单仓单 PR 模型与该仓既有的 registry 双仓 back-port 流程冲突，而本流水线的第一个实施任务（改 `task-management` 模块）本身就是双仓。
- R8-02：D3 称 `changeClass`「由判据计算」，但五条判据中三条只能从自由文本推断。
- R8-01：D3 的判据「改动文件数超过 20」是事后量，建任务时无法求值。
- R8-04：D4 闸门 4「失败超预算」没有 N 次与 M 行，闸门退化为提示。
- R8-05：D4 闸门 5 称「真正有效的是远端 ruleset」，但 ruleset 只约束 git 引用更新，不覆盖 `aws ssm send-command`、`aws s3 rm`、`docker` 等破坏性路径。

这五条同源：**ADR-054 用「应当如此」的语言描述了一组需要具体值的机制**。本 ADR 只做一件事——把落点补成可求值、可拦截、可复核的形式，不改变 ADR-054 的问题判断与总原则。

## 决策

### A. 跨仓任务是串行子任务组，不是一个更大的单仓任务（补 D1）

跨仓任务**不**拆成两个独立设计单元，而是**一个父任务下的串行子任务组**：

```
父任务（DESIGNED，designRef 写明 back-port 范围）
   │
   ├─ 子任务 1  consumer 仓（如 nightwatch-backend）
   │            完整验证：build / lint / 测试 / 验收标准
   │            ✅ 完成后才允许开工下一条
   ▼
   └─ 子任务 2  registry 仓（如 newbie-modules）
                验收 = diff -rq <consumer>/src/modules/<key> <registry>/packages/modules/<key> 输出为空
```

配套约束：

1. **串行由字段强制，不靠人记**。任务新增 `dependsOn: string[]`（可空）。dispatcher 只取「自身能开工且 `dependsOn` 全部为 COMPLETED」的队首任务。这使 D5-3（agent 不得自行调整工作顺序）从纪律变成机制。
2. **registry 子任务的验收是字节一致，不是重跑测试**。`diff -rq` 为空强于重跑测试套件：它证明搬运无损，而测试只证明某个副本能过。registry 侧按 `newbie-modules/AGENTS.md` 的既有约定不重跑测试与 format，consumer 侧的验证输出随父任务留存，作为唯一验证证据。
3. **单条子任务仍是一个 worktree、一条 `task/*` 分支、一个 PR**。D1 的隔离与合并约束不变，跨仓不引入新的分支拓扑。
4. **跨仓任务必然是 `DESIGNED`**，`designRef` 必须写明：模块 key、两侧路径对、consumer 侧验证命令。缺任一项，闸门 1 拒绝开工。

### B. 准入语义：显式影响面声明 + 机械推导 + 闸门复检（取代 D3）

原 D3 的矛盾在于「声称由判据计算」，而判据本身需要语义理解。改为三段式：**声明 → 推导 → 复检**。

**B1 声明**。任务在创建时携带 `impact`（可空对象），四个子字段，由设计阶段（父任务或人）填写，不由 agent 推断：

| 子字段             | 语义                                 | 复检方式（闸门 2 / CI）                              |
| ------------------ | ------------------------------------ | ---------------------------------------------------- |
| `repos`            | 预期改动的仓（仓库 key 枚举）        | 实际改动仓集合必须 ⊆ `repos`                         |
| `touchesSchema`    | 是否动 `prisma/schema.prisma` 或迁移 | 实际路径命中 schema / `migrations/` 却未声明即失败   |
| `touchesContracts` | 是否动跨模块 / 跨仓契约              | `designRef` 列出契约文件清单，实际路径命中却未声明即失败 |
| `irreversible`     | 是否含不可逆操作                     | 执行器升级边界命中时比对声明，未声明即停             |

**B2 推导**。`changeClass` 是纯函数，无自由文本分支：

```
DESIGNED iff repos.length > 1
         || touchesSchema
         || touchesContracts
         || irreversible
         || scopePaths.length > 20
否则 SIMPLE
```

`SIMPLE` 免 `designRef`，但**不免 `impact` 声明**。原 D3 的「豁免条件由判据算出、不接受人工声明」自相矛盾，此处修正：`SIMPLE` 是四元组为空/小且 `scopePaths` 不超 20 的**结果**，声明仍是必填输入。

**B3 复检**。声明错了由闸门抓，不靠声明人诚实：

- 实际仓集合 ⊄ `repos`，或实际路径 ⊄ `scopePaths`，或命中 schema / 契约清单却未声明 → 闸门 2 停手，任务退回 DEVELOPING，差异清单附给会话。
- 同一子任务重复触发（连续 2 次）计入闸门 4 的失败计数，避免「改声明绕过」。

**B4 20 的计量对象改为 `scopePaths` 条数**。原是「改动文件数」，属事后量，准入时不可判定。改为设计阶段填写的 `scopePaths` 条数——可从任务拆解直接数出。实测改动文件数不参与准入，只由闸门 2 用「⊆ `scopePaths`」约束；超出即停。两个数字职责分离：**准入用声明值，执行用实测值，永不做「事后补判」翻转 `changeClass`**。

### C. 闸门 4 的阈值（取代 D4 闸门 4 行）

| 计数器   | 阈值                      | 计量口径                                                       |
| -------- | ------------------------- | -------------------------------------------------------------- |
| 同类失败 | 连续 2 次                 | 指纹 = 闸门编号 + 归一化错误摘要；不同闸门不互相累计           |
| 累计改动 | 单子任务 > 600 行         | add + del；排除 lockfile、`dist/`、生成物、快照、`*.min.*`     |
| 墙钟     | 单子任务 > 45 分钟        | 从 worktree 创建到 push 或放弃                                 |
| 提交次数 | 单子任务 > 3 次 push      | 含 force-push                                                  |

任一触发 → dispatcher 杀掉会话，任务转 BLOCKED，`blockedReason` 写明触发项与计数值，通知人。

计数器由 **dispatcher 持久化**（本地状态文件），跨会话、跨 agent 重启**不重置**；只有人显式 reset 才清零。agent 不可读写该计数——这是闸门 4 唯一有效的原因：它与被约束对象分离。

首版取值为工程估计，实施后按真实会话数据调整；调整通过修改 dispatcher 常量完成，不改本 ADR。

### D. 闸门 5 的真实硬闸是凭证与能力最小化（取代 D4 闸门 5 行）

**先更正覆盖声明**：远端 ruleset 只约束受保护分支的 git 引用更新，**不覆盖** `aws ssm send-command`、`aws s3 rm`、`docker compose down`、`docker run -v /:/`。ADR-054 把 ruleset 当作闸门 5 的硬闸属于虚假保证，此处撤回。

真实硬闸按必要性排序：

1. **agent 不在宿主直跑，只跑在无凭证容器内**。执行器代其发起命令（含 `docker exec`）；agent 自己不持有宿主 docker socket，不挂载 `/root/.aws`、不注入 SSM / S3 写凭证、无云控制面网络出口。
2. **部署动作由执行器的独立进程执行**，其凭证不进入 agent 环境。agent 只能「请求部署」，不能执行部署。
3. **网络出口白名单**：agent 容器出站仅放行包源与 git 远端，其余 deny。作为凭证未泄漏时的纵深。

本地 deny-list wrapper 与 ruleset 均降级为**补充**，不承担覆盖率声明。

若某次实现因成本保留 agent 直接 docker 访问或凭证挂载，该次实现必须**显式声明闸门 5 未闭合**，且不得在无凭证的宿主之外运行流水线。这条是硬约束：宁可说「没闸」，不可说「有闸」。

## 被拒绝的方案

| 方案                                             | 拒绝理由                                                           |
| ------------------------------------------------ | ------------------------------------------------------------------ |
| 跨仓拆成两个独立父任务                           | 丢失串行依赖与验证证据链，registry 侧变成无人担保的孤儿提交        |
| registry 子任务重跑全套验证                      | 违反 registry 既有约定，且重跑证明力弱于 `diff -rq` 字节一致       |
| 继续从任务文本推断影响面                         | 这就是 R8-02 指出的缺陷，换措辞不改变不可求值的事实                |
| 把 20 改为「实际 diff 文件数」                   | 事后量不能做准入；开工后翻转 `changeClass` 会破坏闸门 1 的语义     |
| 用静态分析自动推断影响面                         | 成本高于收益，且推断不可靠——不如显式声明 + 闸门复检               |
| 只靠 ruleset 兜底破坏性操作                      | ruleset 不覆盖非 git 破坏性路径，属虚假保证                        |
| 预算阈值留待「实施时再定」                       | 唯一抵抗自我辩护的闸门没有数值即不存在                             |

## 影响

- **ADR-054**：状态行注明 D1 跨仓形态、D3、D4 闸门 4/5 由本 ADR 取代；正文封存不改。
- **nightwatch-backend**：任务模型在 ADR-054 字段之外新增 `impact`（四子字段）与 `dependsOn`；`changeClass` 由 `impact` + `scopePaths` 推导而非存值；闸门 1（`designRef` + `impact` 完整性）与闸门 2（`repos` / `scopePaths` / 契约清单复检）落在 `task.service` 与 PR CI。
- **本机执行器**：必须实现「容器内运行、无部署凭证、无宿主 docker socket、命令由执行器代发」；闸门 4 计数器持久化且 agent 不可读写；`dependsOn` 预过滤。这些从「实现细节」升级为**准入条件**——不满足则不得宣称闸门闭合。
- **newbie-modules**：back-port 段补充 registry 子任务验收口径（`diff -rq` 为空 + 不重跑测试）。
- **findings**：R8-01 ~ R8-05 状态置 `fixed（ADR-055）`；R8-06 ~ R8-12 保持 open，不在本 ADR 范围。

## Cross-host check

| 维度       | 框架 / registry 层                                     | 宿主层                                                     |
| ---------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| 跨仓形态   | `dependsOn` 与「子任务组」语义通用，registry 模块自身同样受 `diff -rq` 验收 | 具体模块 key、两侧路径对、验证命令由宿主填写               |
| 准入声明   | `impact` 四子字段与 `changeClass` 推导规则通用         | 仓库 key 枚举、契约文件清单由宿主提供                      |
| 闸门阈值   | 阈值口径（同类失败 / 累计行 / 墙钟 / 提交数）通用      | 具体取值由执行器常量持有，可按宿主调整                     |
| 凭证边界   | 不定义；凭证与网络属部署形态                           | 本机执行器的容器形态、无凭证要求、出口白名单是 nightwatch 特有 |
| 可移植性   | 任意宿主装配同一模块即获得相同的准入与串行语义         | 执行器实现形态不可移植，也不应被其他宿主复用               |
